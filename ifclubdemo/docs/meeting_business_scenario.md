## 1. 场景定义与背景

### 1.1 一句话说明

> 办公室里要订会议室：能看到有哪些房间、能提交预订；合法的留下，撞车或违规的被明确拒绝并说清原因。

### 1.2 背景设定

| 项 | 填写 |
| --- | --- |
| 想定起点时间 | 演示当日（本地可反复重置数据） |
| 主要对立方 / 参与方 | 预订人 ↔ 会议室资源占用 |
| 触发事件简述 | 多人同时想订同一间房的相近时段 |
| 公开宣称目标（如有） | 防撞车、防订停用房、失败说得清 |
| 本场景采用的事实边界 | 本地小演示，不做企业级会议室平台 |

### 1.3 要解决的业务 / 决策问题

| 编号 | 问题描述 | 现在怎么做 | 期望用本体改进什么 |
| --- | --- | --- | --- |
| P1 | 同一间房时段撞车 | 口头约或事后才发现 | 保存前按规矩拒绝并提示 |
| P2 | 订了停用/维修房 | 名单未区分或未拦截 | 只能订启用中的房间 |
| P3 | 失败原因不清楚 | 页面像成功又像失败 | 明确拒绝 + 可读原因 |
| P4 | 规矩只在人口头 | 换入口易绕过 | 规矩写进说明书并由系统统一执行 |

### 1.4 成功标准（验收口径）

- [ ] 能查看会议室名单（含是否启用）
- [ ] 能提交预订（主题、预订人、开始/结束时间）
- [ ] 合法预订能留下，刷新后还在
- [ ] 冲突或违规被拒绝，并说明原因；列表无脏数据
- [ ] 首尾相接可以订；坏时间、停用房订不了
- [ ] 页面有简短操作说明与规则说明；冲突红字提示

## 附录 · 规矩摘要（对生成提示词可粘贴）

必须做到：

- 结束时间要晚于开始时间  
- 同一会议室时段不能重叠（首尾相接可以）  
- 只能订启用中的会议室  
- 冲突时由系统拒绝，页面只负责提示  

本演示不做：审批、登录权限、消息通知、按人数卡容量、复杂日历。  

提醒：能不能订，由系统按规矩说了算。
