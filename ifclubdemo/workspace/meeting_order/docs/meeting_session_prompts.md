# 会议室预订 · 双 Session × 10 轮提示词（白话）

> 风格对齐讲义附录「十轮提示词示例」：**少技术黑话、一轮一事、写清验收**。  
> Session A / B **全部白话**（按决策：不在 B 突然改成术语堆砌）。  
> 生成方式：优先 `ifclubdemo` CLI/EP + 百炼 30B 编码模型。  
> 每轮开头可加固定句：「请先阅读业务说明书与规矩摘要；只做本轮要求，不要扩大范围。」

配套：

- 业务说明书：`docs/meeting_business_scenario.md`  
- 测试计划：`docs/meeting_test_plan.md`

## Session A · 搭出可演示闭环（10 轮）

### A1 · 说清要解决什么

```
我们要做一个很小的「会议室预订」演示，不是完整办公套件。

请先帮我用普通人能听懂的话，写清三件事：
1）办公室里订会议室，最常见的痛点是什么（至少写：撞车、订了停用房、失败了却不知道原因）
2）这个演示做到什么程度就算成功：能查看会议室、能提交预订、合法的能留下、冲突或违规的要明确拒绝并说明原因
3）明确不做哪些事：审批、登录权限、消息通知、按人数卡容量、复杂日历

先只写说明，不要开始搭系统。写完后用三句话总结「范围内 / 范围外」。
```

**本轮验收**：有范围说明；未改业务代码。

---

### A2 · 把规矩写成说明书

```
请根据上一轮的范围，写一份「规矩说明书」，用普通人能看懂的中文，不要术语。

必须写清：
- 结束时间必须晚于开始时间
- 同一间会议室，时段不能重叠；上一场结束时刻正好等于下一场开始时刻（首尾相接）可以
- 只能订「启用中」的会议室；停用的订不了
- 冲突或违规时，系统必须拒绝保存，并告诉用户原因；页面不能假装订成功
- 能不能订，以系统按规矩检查的结果为准，不要只靠页面上随便拦一下

另外写一小段「本演示不做」：审批、登录权限、消息通知、按人数卡容量、复杂日历。

先只产出说明书。完成后告诉我：以后改规矩时，应该先改这份说明书，再改系统行为。
```

**本轮验收**：规矩说明书齐；未搭页面。

---

### A3 · 先有会议室名单

```
请按说明书开始搭这个演示的第一步：先准备好「会议室名单」。

要求：
1）每间会议室至少有：名称、大约能坐多少人（只用来展示，不按人数拦预订）、是否启用
2）预置几间启用中的会议室，再预置一间停用的（比如维修中），方便后面演示「订不了」
3）我本地能一键初始化，之后能再次清空重来

这一轮不要做预订表单，也不要做冲突检查。完成后告诉我：怎么初始化、怎么确认名单已经在。
```

**本轮验收**：可初始化；名单含启用+停用。

---

### A4 · 能把合法预订留下来

```
在会议室名单已经就绪的基础上，请加上「预订记录」的保存能力。

一条预订至少包含：订哪一间、会议主题、预订人、开始时间、结束时间。
这一轮先假设提交的都是合法信息：时间合理、房间启用、也不撞车。
请做到：保存成功后，我能再次查看这些预订，刷新或重开之后记录还在。

暂时不要做页面，也不要做冲突拦截。完成后告诉我怎么新增一条、怎么查看列表。
```

**本轮验收**：能新增与再查；数据仍在。

---

### A5 · 拦住时间不合法

```
请先阅读规矩说明书，然后只加强「保存前的检查」，不要做页面。

这一轮只要求：
- 结束时间必须晚于开始时间；相等或结束更早 → 拒绝保存，并给出清楚原因
- 检查不通过时，系统里不能留下半条脏记录

请给我两种可亲手试的例子：一条时间合法应成功；一条时间不合法应失败并看到原因。
```

**本轮验收**：对应测试 T-R01；无脏数据。

---

### A6 · 拦住撞车和停用房

```
请继续只改「保存前的检查」，对齐规矩说明书，仍然不要做页面。

增加这些规则：
1）同一间会议室，新预订与已有有效预订的时段不能重叠
2）首尾相接不算冲突（例如 10:00–11:00 与 11:00–12:00 都可以留）
3）不同会议室互不影响
4）停用中的会议室一律拒绝新预订

冲突或违规时必须拒绝保存，并给出普通人能懂的原因（例如「该时段会议室已被预订」）。
请给我可亲手试的例子：成功一条、重叠失败一条、首尾相接成功一条、停用房失败一条。
```

**本轮验收**：T-R02～R05。

---

### A7 · 做出能提交的预订页

```
现在请做一个简单的预订页面，中文界面，一个页面就够。

页面上要能：
1）选择会议室（停用的可以看见，但不要让人轻易订进去；最终仍以系统检查为准）
2）填写会议主题、预订人、开始时间、结束时间
3）点提交

提交时，必须走已经写好的规矩检查：通过才留下记录；不通过就失败，不要在页面上假装成功。
风格简洁即可。这一轮先把「能提交」做通；列表和红字提示可以下一步再加强。
完成后告诉我怎么打开页面、怎么订一笔成功的。
```

**本轮验收**：能打开页并订成功一笔（E2E-A 雏形）。

---

### A8 · 页面上能看见名单和已有预订

```
请完善预订页，让演示时一眼能看懂现状。

需要：
1）能看到会议室一览（名称、是否启用等）
2）能看到已有预订列表（哪间房、主题、谁订的、起止时间）
3）提交成功后，列表应出现刚订的那条；刷新后还在

不要改规矩本身。不要做成复杂日历。完成后告诉我怎么快速确认：名单在、列表在、新预订能出现。
```

**本轮验收**：名单+列表可见；刷新仍在。

---

### A9 · 订不上时用红字说清楚

```
请只改页面上的失败提示，不要在页面里自己另写一套「会不会撞车」的判断来代替系统检查。

要求：
1）系统因冲突拒绝时，用红色文字提示类似「该时段会议室已被预订」
2）时间不合法、房间停用等其他失败，也用红色文字显示系统给的原因；没有原因就显示「预订失败」
3）失败时，列表里不要多出脏数据
4）成功时，清空错误提示，并刷新预订列表

请顺便在页面上加两三句操作说明：先订一笔成功的，再故意订重叠时段，应看到红字。
```

**本轮验收**：E2E-B；T-A04。

---

### A10 · 规则说明摆上台面并走通演示

```
请在预订页旁增加一块「规则说明」（侧边或上方卡片均可），用普通人能看懂的中文写清，内容对齐规矩说明书：

必须做到：
- 结束时间要晚于开始时间
- 同一会议室时段不能重叠（首尾相接可以）
- 只能订启用中的会议室
- 冲突时由系统拒绝，页面只负责提示

本演示不做：
- 审批、登录权限、消息通知
- 按人数卡容量
- 复杂日历

并写一句提醒：能不能订，由系统按规矩说了算。

不要改检查逻辑，只改展示。做完后请帮我确认这两条路径都能用：
A）订一笔合法的 → 成功，列表出现
B）同一房间再订重叠时段 → 红字拒绝，列表不多脏数据
```

**本轮验收**：规则说明可见；A/B 双路径通过。

## Session B · 白话加固（仍少术语，10 轮）

> 目标：把「页面归页面、检查归检查、存取走统一出口、自动测试能拦住跑偏」说清楚并落到系统里。  
> 仍用白话；必要时只用极少固定名字（如房间字段名），不堆框架名词。

### B1 · 把职责说清楚再改结构

```
请先阅读业务说明书与规矩摘要。

现在系统已经能演示订会议室。请用普通人能懂的话，先写清四类职责，再按职责整理代码位置（先说明再小步调整，不要一次大翻）：
1）给人填表、看列表、看红字的部分
2）专门按规矩判断「能不能订」的部分（不要访问存数据的细节）
3）真正把会议室/预订存进去、取出来的部分
4）把「人的请求」翻译成系统能懂的一句话、再去调用检查与存取的部分

要求：填表页面里不要自己另写一套撞车算法当唯一防线；能不能订以检查部分为准。
本轮做完后，告诉我各类职责分别落在哪些文件夹/文件，并跑通：合法预订仍成功。
```

**本轮验收**：职责说明清晰；合法路径未坏。

---

### B2 · 把提交内容的「固定说法」钉死

```
请继续白话、小步改。

新建预订时，人提交的内容字段名必须固定，不要一会儿换说法：
- 订哪间、主题、预订人、开始时间、结束时间（实现里用统一英文字段名，且与说明书附录一致）

请增加一层「只负责接收与整理提交内容」的位置：检查字段是否齐全、格式是否对，然后交给后面的检查与保存。
不要在这一层写撞车算法。

做完后给我一个成功提交例子、一个缺字段或坏时间被拒的例子。
```

**本轮验收**：字段固定；坏输入可拒。

---

### B3 · 存取走统一出口（可换库的准备）

```
请继续白话、小步改。

请把「存会议室/预订、取列表」收成统一出口：业务检查与页面都不要各自偷偷连库。
默认用本地文件型小库即可；同时留一个「将来可换成另一种库」的同一套出口说法（现在不必真连上另一种库）。

测试时必须能指到临时库，避免弄脏演示数据。
做完后：初始化名单、新增合法预订、再查列表，三条都通。
```

**本轮验收**：存取经统一出口；临时库测试可用。

---

### B4 · 先写规矩的自动检查

```
请测试优先：先补「规矩检查」的自动用例，再按需改实现。

至少覆盖：
- 结束不晚于开始 → 失败
- 同房重叠 → 失败
- 首尾相接 → 成功
- 停用房 → 失败
- 不同房间同时段 → 互不影响

不要做页面。做完后让这些自动检查都通过，并告诉我怎么本地跑。
```

**本轮验收**：T-R01～R05 全绿。

---

### B5 · 把「办事员」串起来

```
请用白话小步改：增加一层专门「办事」的部分——收到整理后的提交后，先问规矩检查，通过了再让存取出口保存；失败就把原因原样往回传。

页面和入口不要绕过这层直接改库。
做完后：合法预订成功；重叠预订失败且有原因。
```

**本轮验收**：编排清晰；E2E-A/B 的后端侧仍对。

---

### B6 · 对外入口与自动检查

```
请补齐「对外入口」：能列出会议室、能列出预订、能新建预订。
冲突时必须明确失败，并带上「冲突」含义的错误标记，方便页面显示红字。

请同时补入口的自动检查（用临时库），覆盖：成功创建、重叠失败、失败后列表条数不变。
本轮仍少改页面。做完后告诉我怎么跑这些自动检查。
```

**本轮验收**：T-A01～A04。

---

### B7 · 页面只做展示与提交（白名单）

```
请只改页面相关部分，保持白话约束：
- 不要在页面里自己判断会不会撞车
- 只用约定好的几个页面和小组件，不要额外发明一堆页面
- 样式简洁统一，不要引入花哨组件库
- 不要用奇怪的路径缩写写法（禁止 @/ 这类别名）

页面仍要能：选房、提交、看列表、看红字、看规则说明与操作说明。
做完后构建/打开页面，走一遍成功预订。
```

**本轮验收**：T-F*；页面演示成功。

---

### B8 · 把说明书变成系统开局约定

```
请把业务说明书与规矩摘要、测试计划，变成这个演示项目开局就能加载的约定（记忆/说明文件），让后续生成轮次先读再改。

然后做一次自检：约定已加载；合法预订与冲突拒绝仍可用。
不要扩大功能范围。
```

**本轮验收**：inject 类步骤完成；双路径仍通。

---

### B9 · 专修失败项

```
请根据最近一次自动检查或演示失败的原因，只修相关的一小处，不要顺手重构。

修完后重新跑：规矩用例 + 入口用例 + 页面构建。
全部通过再结束本轮。
```

**本轮验收**：失败项清零或明确无失败。

---

### B10 · 全量回归与演示收口

```
请做收口，不要加新功能：
1）跑全部自动检查与页面构建
2）亲自确认演示路径：
   A）合法预订成功，列表有记录
   B）重叠预订红字拒绝，列表无脏数据
   C）首尾相接可订；停用房/坏时间被拒
3）用几句话告诉我：怎么启动、怎么重置名单、怎么给别人演示

完成后给出一份简短验收清单勾选结果。
```

**本轮验收**：全绿 + 可演示。
